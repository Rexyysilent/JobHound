# Buyer scope and budget revisions

New public thread captures use `community-thread/v2`. Buyer-authored original
posts, explicit scope/budget changes and closing/reopening statements retain
native post IDs, actor IDs, creation/edit timestamps and normalized material
text hashes. The original request date never becomes capture time, a recent
reply date or an edit date. Prior in-place edit bodies are unavailable from one
current capture; the schema says so rather than reconstructing them.

An explicit later buyer budget declaration supersedes earlier advertised buyer
amounts for selection. A scope change without a new declared budget invalidates
the earlier amount for the changed scope. Earlier amounts remain in the full
description and pay-candidate audit with their native actor, exact text span,
post path and cooked-body hash. They receive `historical_thread_terms`, so they
cannot set current pay or create a false old-versus-new pay conflict. Active
changed terms carry the revision ID in their request scope.

Missing/future/backwards revision dates, incomplete thread coverage or an older
monetary post edited after the apparent replacement leave current terms unknown.
Such claims receive `unresolved_thread_terms`; no supported supersession edge or
current revision is asserted. Provider post numbers can establish sequence for
equal native creation timestamps. A raw edit timestamp is retained as provenance
and does not prove a substantive edit or create fresh demand.

Revision recognition is deliberately narrow: explicit declarative scope and
budget markers. Questions, routine thanks, seller replies and quotes cannot
establish changed buyer terms. Unsupported phrasing remains ordinary captured
text and needs interpretation; this is not complete semantic coverage of every
possible negotiation. No individual agreement, task allocation or payment is
inferred from a public budget. Ambiguous amounts stay visible in the audit.

The action policy adds a precise verification task for changed or unresolved
terms and preserves the exact request route. Supported public scope changes
remain Verify until the relevant facts are checked; they do not establish a
personal buyer reply or authorize work. Existing location and paid-intent checks
retain precedence. Closed requests remain Skip.

Material revision identity excludes capture time, formatting whitespace, case
and edit metadata alone. These IDs supply evidence for later presentation and
delivery integration. This change does not add notification delivery, a freshness
or priority boost, outcome agreement mapping, or an automatic cross-capture edit
history. Those are separate handoff requirements.

Existing `community-thread/v1` observations are re-derived using their original
contract and exact serialized field set. Their description and pay semantics
remain unchanged during replay; they are not silently relabeled as v2. New v2
metadata is also re-derived from native pages, so a tampered revision label or
current-post list is rejected.

Only economics is selected by revision here. Requirement and role-fit extraction
still inspects retained buyer prose; earlier skill or geography claims are not
mechanically superseded by a budget/scope marker. Those claims need separately
supported revision semantics.
